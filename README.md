# SHOWROOM Analytics

[SHOWROOM](https://www.showroom-live.com/) の **ギフターの分析と、イベントの作戦** のためのシステムです。
ルーム・イベント・貢献ランキング・ギフト・配信の記録を集めて残し、管理画面で、ギフターの動き・ルームの強さ・
イベントの必要ポイント・大会の勝ち上がりなどを見られます。
あわせて、ログインした状態で指定したルームの視聴を続け (ヘッドレス Chromium・Playwright。止まったら自動で復旧)、
配信のギフトやコメントを記録します。

> 名前について: 2026-10-19 に「SHOWROOM keeper」から「SHOWROOM Analytics」に変えました。変えたのは画面と説明書の名前だけで、
> プログラムの名前 (`showroom_keeper`・Docker・自動の更新・`.env` の `SHOWROOM_` で始まる設定) は前のままです。

> Mac から管理画面を開くときは、[tools/管理画面を開く.command](tools/管理画面を開く.command) をダブルクリックすると、サーバーへのつなぎ道を開いてブラウザで管理画面を開きます (切れても自動でつなぎ直し、開いている間は Mac をスリープさせません)。
>
> 作業する人へ: サーバーで今どう動いているかと、守る方針は [docs/現状.md](docs/現状.md) に、これから作るとよい機能の案は [docs/改善アイデア.md](docs/改善アイデア.md)、作戦の相談相手 (Claude Code のエージェント) は [docs/データ分析戦略部隊.md](docs/データ分析戦略部隊.md) にまとめています。作業を始める前に読んでください。

## 主な機能

| 機能 | 内容 |
| --- | --- |
| ログイン維持 | ID/パスワードで自動ログイン、または手動ログインしたセッション (Cookie) を保存して再利用。ログインはアカウント単位なので、2 時間ごとに 1 ルームだけで確認し、切れていれば再ログインして各ルームのページに反映する |
| 配信待機 | メモリに余裕があれば、配信していないルームのページも開いたままにする。配信が始まったらそのページで視聴を始め、終わってもページは閉じない。メモリが足りない時は配信中のルームだけ開く (`keep_open_when_offline` で指定可) |
| 再生監視 | 動画の再生位置が進んでいるかを定期確認。止まっていれば再生を再開し、一定回数続けばページをリロード |
| 定期リロード | 長時間視聴でのメモリ増加やセッション劣化を避けるため、一定間隔でリロード |
| 障害復旧 | ネットワーク断・ページクラッシュ・ブラウザ終了を検知し、指数バックオフで自動再起動 |
| 複数ルーム | 指定した全ルームを同時に監視する (ルームごとにタブを分離し、それぞれログインしたままにする) |
| 観客席のアバター | 視聴しているルームで、配信中に 10 分ごとに、観客席 (ステージ) に自分のアバターがいるかを確かめる (確かめる時の問い合わせで入り直しになる)。いなければ 90 秒後に確かめ直し、ページがログインしていなければ読み込み直す。結果は管理画面の「ライブ」のルームのカードに出る |
| 配信開始時の入室 | 視聴はしないルームを別に指定しておくと、配信が始まった時に一度だけ、ブラウザのページを開かずに入室する (入室のお知らせとアバターも出る) |
| 視聴時間ログ | ルームごとの累計視聴時間をログ出力 |

## セットアップ

Python 3.9 以上と **Google Chrome** が必要です。
Playwright 付属の Chromium は H.264 に非対応で SHOWROOM の映像を再生できないため、インストール済みの Chrome を使います
(Chrome が無い場合は警告を出して付属 Chromium で起動します)。

```bash
git clone https://github.com/mutsu-6/SHOWROOM-log-in-System.git
cd SHOWROOM-log-in-System
python -m venv .venv && . .venv/bin/activate
# Apple Silicon の Mac では Intel 版 Python だと極端に遅くなるため、代わりに次を推奨:
#   arch -arm64 /usr/bin/python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
playwright install chromium   # Chrome が無い環境向けの予備

cp config.example.yaml config.yaml   # rooms を編集
cp .env.example .env                 # 必要ならログイン情報を記入
```

## ログイン

次のどちらかを使います。

1. **手動ログイン (推奨・CAPTCHA にも対応)**

   ```bash
   python -m showroom_keeper login
   ```

   ブラウザが開くので SHOWROOM にログインし、ターミナルで Enter を押します。
   セッションは `state/storage_state.json` に保存され、以後の起動で自動的に使われます。

2. **自動ログイン**

   `.env` (または環境変数) に `SHOWROOM_ACCOUNT_ID` / `SHOWROOM_PASSWORD` を設定しておくと、未ログイン時やセッション切れ時に自動でログインします。
   CAPTCHA を要求された場合は自動ログインできないため、1 の手動ログインを行ってください。

ログインしなくても匿名で視聴状態は維持されます。

## 起動

```bash
# config.yaml の rooms を監視
python -m showroom_keeper run

# ルームを引数で指定 (URL / room_url_key どちらでも可)
python -m showroom_keeper run https://www.showroom-live.com/r/ROOM_URL_KEY other_room

# ブラウザ画面を表示して動作確認
python -m showroom_keeper run --headed
```

`Ctrl+C` (SIGINT) / SIGTERM で、セッションを保存してから安全に終了します。

- 管理画面が要らなければ `run --no-web` または `web_port: 0`。ポートは `SHOWROOM_WEB_PORT` で変更できます。

### 常駐させる

- **サーバー (24 時間稼働)**: Ubuntu 22.04/24.04 (x86_64、メモリ 2GB 以上推奨) のサーバーを用意し、
  手元の PC (`login` 済み) から次を実行します。フォルダとログイン状態をコピーし、
  Docker のインストールから起動まで自動で行います。サーバー再起動後も自動で再開します。

  ```bash
  cd ~/SHOWROOM-log-in-System
  rsync -a --exclude .venv --exclude .git --exclude data ./ ユーザー名@サーバーのIP:SHOWROOM-log-in-System/
  ssh -t ユーザー名@サーバーのIP 'sudo bash SHOWROOM-log-in-System/deploy/setup-server.sh'
  ```

  2 回目からの更新は、Mac のデスクトップの「サーバーを更新する.command」(`tools/サーバーを更新する.command`) をダブルクリックするか、
  サーバーで `cd ~/SHOWROOM-log-in-System && git pull && bash tools/update.sh` を実行します (くわしくは [docs/サーバーの更新.md](docs/サーバーの更新.md))。ログは `ssh ユーザー名@サーバーのIP 'cd SHOWROOM-log-in-System && sudo docker compose logs -f'` で見られます。
- **メモリの目安**: 既定では指定した全ルームのページを常に開いておくため、ルームの数だけメモリを使います。
  計測では 1 ルーム目で約 0.6〜1GB、以降 1 ルームにつき約 0.5GB 増えました (3 ルームで約 1.9GB)。
  既定では、全ルームを開いてもメモリが足りる時だけ配信していないルームのページも開いておき、足りなければ配信中のルームだけ開きます
  (例: メモリ 2GB のサーバーで 5 ルームなら配信中だけ)。`SHOWROOM_KEEP_OPEN_WHEN_OFFLINE=true` / `false` で固定できます。
  ログインはルームごとではなくアカウント単位で全ページ共通のため、この設定でもログイン状態の確認・再ログインは同じように行われます。
- **Docker (手動)**: `.env` を用意し `docker compose up -d`。セッションは `./data/storage_state.json` に保存されます。
- **systemd**: `deploy/showroom-keeper.service` を参照。

## 手動でコメントする

視聴 (`run`) を動かしたまま、別のターミナルから配信にコメントを 1 件ずつ投稿できます。
開いている配信ページのコメント欄から送信し、コメント履歴に載ったことを確認して結果を表示します。

```bash
# 手元の PC で run している場合
python -m showroom_keeper comment こんにちは
# サーバー (Docker) の場合
~/SHOWROOM-log-in-System/deploy/comment.sh こんにちは
```

本文を省略すると会話モードになり、1 行入力して Enter を押すたびに投稿します (`/q` または Ctrl+D で終了)。
サーバーで `bash ~/SHOWROOM-log-in-System/deploy/comment.sh --install` を一度実行すると、
`c こんにちは` (1 件投稿) や `c` (会話モード) と短く打てるようになります。

- 1 件 50 文字まで。複数ルームを監視していて配信中のルームが複数ある場合は `--room ルーム名` で投稿先を指定します (配信中が 1 つなら自動)。
- 連投を防ぐため、投稿と投稿の間は最低 3 秒空けます。自動・定期投稿の機能はありません
  (SHOWROOM の利用規約はボット等による自動化された利用を禁止しています)。

## 配信状況を確認する

```bash
python -m showroom_keeper status          # 手元の PC
~/SHOWROOM-log-in-System/deploy/status.sh  # サーバー (Docker)。-w 60 で 60 秒ごとに更新
```

- **リアルタイム視聴者数**: サロン形式の配信のみ。視聴中の keeper が 60 秒ごとに SHOWROOM の在室確認 API
  (`/api/viewer_presence/heartbeat`) に問い合わせて取得します (要ログイン)。
  クラシック形式では公式ページもこの API を使わず人数が意味を持たないため、問い合わせず「非公開」と表示します。
  `viewer_count: false` で無効にできます。
- **推定アクティブ人数**: クラシック形式の同接の目安。配信ページが受信するリアルタイム通信のうち、
  直近 10 分間に入室・コメント・ギフトのいずれかをしたユーザー数です (受信を読むだけで送信はしません)。
  見ているだけの人は数えられないため、実際の同接より少なくなります。開始から 10 分未満は観測時間も表示します。
- **ログイン状態**: 視聴中の keeper が 2 時間ごとに API で確認した結果です (`login_check_interval` で間隔を変更可)。
  確かめるのはアカウントのログインで、どのルームで聞いても同じなので、問い合わせは見張っているルームの 1 つで 1 回だけです
  (ルームへの入室やコメントはしません)。入室するルームだけを指定している時は、配信中のルームを 1 つ使います。
  確認できなかった時 (通信の失敗など) は再ログインせず、次の確認を待ちます。起動時にも確認し、切れていれば ID・パスワードの設定があれば再ログインします。
- これらは視聴 (`run`) 中のみ表示されます。
- **盛り上がり度**: SHOWROOM が画面に表示している値です (視聴者数ではありません)。
- **直近 10 分のコメント人数**: 直近 10 分間にコメントしたユーザー数です。

## ギフト履歴を見る

```bash
python -m showroom_keeper gifts                       # 手元の PC (今回の配信)
~/SHOWROOM-log-in-System/deploy/gifts.sh --hours 24   # サーバー。--top 人数 / --log 件数 も指定可
```

見張っているルームについて、リスナー別のギフト合計 (ポイント・個数・回数・内訳) のランキングと、最近のギフトを表示します。

- 視聴 (`run`) 中は、配信ページが受信するギフトのお知らせ (無料の星を含む) をすべて `gifts/<ルーム>.jsonl` に記録します
  (`record_gifts: false` で無効)。
- SHOWROOM のギフト履歴 API (直近 100 件、主に有料ギフト) も合わせて読み、重複を除いて集計します。
- ポイントは有料ギフトと無料ギフト (星・種・無料プレゼントなど) に分けて表示します (例: `6,250 pt (有料 6,250 / 無料 0)`)。
- `--user 名前かID` で特定のリスナーの履歴 (合計・日別・一覧) だけを表示します。名前は部分一致、数字はユーザー ID
  (ランキングの `[ID ...]`)。名前で探しても同じ ID の改名前後の分をまとめて表示します。`--all` で記録のすべてが対象です。
- 特定のリスナーが他のルームで送ったギフトは公開されていないため取得できません。

### 配信開始時に一度だけ入室する

```bash
SHOWROOM_ENTER_ROOMS='https://www.showroom-live.com/r/ルームA,https://www.showroom-live.com/r/ルームB'
```

- 視聴はしないルームで配信が始まると、ブラウザのページは開かずに、ログインした状態の Cookie で一度だけ入室します。
  `/api/live/current_user` を呼ぶと観客席 (ステージ) にアバターが並び、続けて `/api/room/greeting` を呼ぶと、
  SHOWROOM が入室のお知らせを流すことがあります (お知らせは毎回ではありません。配信ページと同じ順に呼んで 10 秒待っても、
  流れないことがあります)。greeting には `uuid` の Cookie が要るので、最初の入室で配信ページを 1 回開いてもらい、
  6 時間はほかのルームでも使い回します (断られたらその場で取り直します)。1 回 0.5 秒ほど・問い合わせ 2 回で、
  メモリはほとんど使いません。
  ログインしていない時や失敗した時は入室済みにせず、次の確認で入室し直します (1 つの配信で 3 回まで)。
  同じ配信には一度しか入室せず、次の配信が始まるとまた入室します。管理画面の「設定」からも追加できます。
- 配信状況は `status_poll_interval` (既定 60 秒) ごとに、1 ルームにつき 1 回問い合わせて確認します。
- 入室は 1 ルームずつ順に行うため、多くのルームで同時に配信が始まった時は順に入室します。
- 視聴するルーム (`SHOWROOM_ROOMS`) と重なるルームは、視聴ページで入室済みなので対象外です。
- 入室済みの配信は `state/entered.json` に残すため、keeper を起動し直しても同じ配信には入室し直しません。
- ログインの Cookie は、keeper が開いているブラウザ (ログインを保っているもの) から入室のたびに読みます。

#### SHOWROOM の全ルームで入室する

```bash
SHOWROOM_ENTER_ALL=true
```

- 配信中の一覧 (`/api/live/onlives`、1 回で SHOWROOM 全体) を `status_poll_interval` (既定 60 秒) ごとに 1 回取り、
  新しく始まった配信に一度だけ入室します (入り方は上と同じ)。`SHOWROOM_ENTER_ROOMS` のルームも含みます。
- 入室は 1 件ずつ、1 秒ずつ空けて行います。起動した時に配信中のルーム (夜は 400〜500) にも入るので、
  起動してから 10 分ほどは入室が続きます。
- 有料の配信と、視聴するルーム (`SHOWROOM_ROOMS`) には入りません。
- 入室は 1 日に数千〜1 万回 (問い合わせはその 2 倍) になります。配信ページを開かずに API だけを呼ぶので、
  ふつうの視聴とは違う動きとして見つかりやすい可能性もあります。1 つのアカウントで毎日これだけ入室すると、
  自動の巡回とみなされてアカウントが制限されるおそれがあります。
- 入室ごとの記録 (ログ) は出さず、1 時間ごとに入室した件数だけを出します。
- 1 時間以上配信中の一覧に出てこないルームは、`state/entered.json` から消します (記録が大きくならないように)。

### 視聴せずにギフトだけ記録する (ルーム指定・イベント)

`.env` (または `config.yaml`) で指定すると、ブラウザを開かずリアルタイム通信だけを受信してギフトを記録します。

```
SHOWROOM_RECORD_ROOMS='https://www.showroom-live.com/r/ルームA,https://www.showroom-live.com/r/ルームB'
SHOWROOM_EVENTS='https://www.showroom-live.com/event/イベント名'
```

- ルームもイベントも件数の上限はありません。イベントは参加ルームすべてが対象で、終了日時を過ぎると自動で記録をやめます。
- 保存したログインセッション (`state/storage_state.json`) があれば、記録時の問い合わせと受信にも使います。
- 2 分ごとに配信状況を確認し、配信中のルームだけ接続します。受信のみで、こちらからは何も送りません。
- `python -m showroom_keeper run` (サーバーでは `docker compose up -d`) の実行中に記録します。
  視聴するルーム (`SHOWROOM_ROOMS`) が無くても動き、入室するルーム (`SHOWROOM_ENTER_ROOMS`) も無ければブラウザを起動しません。
- 集計は `g ルーム名` (ルーム単位) と `g --event イベントURL` (イベント全体のルーム別・リスナー別ランキング)。
  `--user` で特定リスナーのイベント内の履歴 (どのルームに送ったか) も表示できます。
- `g --event` では、SHOWROOM 公式の貢献ランキング (各ルームの上位 100 人) も全ルーム分集めて
  「公式の貢献ランキング (イベント全体)」として表示します。記録を始める前の分や keeper を止めていた間の分も含まれ、
  記録のあるルームについては記録と公式の合計を比べて取りこぼしの目安も出します。`--user` でも公式の順位を表示します。
  - 初回は参加ルーム数に応じて数十秒かかります (650 ルームで約 30 秒)。結果は `cache/` に保存し、開催中は 10 分間、
    終了から 1 日たったイベントは期限なしで使い回します。`--no-official` で取得をやめ、記録だけを速く表示します。
  - 公式の値は各ルーム上位 100 人の貢献ポイントだけで、ギフトごとの明細 (いつ・何を送ったか) は含みません。
- ギフトごとの明細を記録できるのは設定してから先の分だけです。過去の配信の明細は SHOWROOM から取得できません。
- SHOWROOM 全体のリスナーを対象にした記録には対応しません。

## 設定

`config.example.yaml` に全項目と説明があります。カレントディレクトリの `.env` は自動で読み込まれ、環境変数は設定ファイルより優先されます。

**どの項目も `SHOWROOM_<項目名を大文字>` の環境変数 (`.env`) で指定できます** (例: `login_check_interval: 7200` → `SHOWROOM_LOGIN_CHECK_INTERVAL=7200`、
真偽値は `true` / `false`)。サーバー (Docker) では `config.yaml` を読まないため、設定は `.env` に書いてください。

| 環境変数 | 内容 |
| --- | --- |
| `SHOWROOM_ACCOUNT_ID` / `SHOWROOM_PASSWORD` | ログイン情報 |
| `SHOWROOM_ROOMS` | 視聴するルーム (カンマ区切り) |
| `SHOWROOM_ENTER_ROOMS` | 視聴はせず、配信が始まったら一度だけ入室するルーム (カンマ区切り)。視聴するルームと重なる分は入室しない |
| `SHOWROOM_ENTER_ALL` | SHOWROOM の全ルームで、配信が始まったら一度だけ入室する (既定 `false`)。1 日に数千回入室するので、アカウントが制限されるおそれがある |
| `SHOWROOM_RECORD_ROOMS` | 視聴せずギフトだけ記録するルーム (カンマ区切り、件数の上限なし) |
| `SHOWROOM_EVENTS` | 参加ルームすべてのギフトを記録するイベント (カンマ区切り、件数の上限なし) |
| `SHOWROOM_RESEARCH_ROOMS` | ギフターを調べるルーム (カンマ区切り)。前の `SHOWROOM_SUPPORT_ROOMS` (応援しているルーム) も読み、調べるルームに入れる (分析でどのルームから見るかは、設定ではなく「ギフター」「イベント」の画面の「見るルーム」で選ぶ)。視聴はせず、各ルームの累計ポイントランキング (上位 30 人)・過去と開催中のイベント・イベントの貢献ランキング (上位 100 人) を集める。管理画面でも変えられ、変えても視聴はやり直さない |
| `SHOWROOM_RESEARCH_BACKUP_TIMES` / `SHOWROOM_RESEARCH_BACKUP_KEEP` | research.db のバックアップを作る時刻 (毎日、日本時間、既定 `4:00`) と残す数 (既定 2)。写しは `data/backup/` に、SQLite のバックアップの仕組みで作る (書き込み中でも壊れない) |
| `SHOWROOM_RESEARCH_DAYS` / `SHOWROOM_RESEARCH_TIMES` | 上の情報を集める曜日と時刻 (日本時間、既定は毎日 `4:30`)。問い合わせは 1 秒ずつ空け、終わったイベントの貢献ランキングは一度取ったら取り直さない。古いイベント (2015 年ごろから) の貢献ランキングも取る |
| `SHOWROOM_RESEARCH_ALL` | `true` で SHOWROOM の全ルームの情報を少しずつ集め続ける (既定 `false`)。配信中のルーム (5 分ごと)・イベントの一覧と参加ルーム (6 時間ごと)・過去のイベント (イベント番号を新しい順に 2014 年までさかのぼる。各ルームのイベントのポイントと順位も残す) からルームを見つけ、各ルームの累計ランキングと、終わったイベントの貢献ランキングを新しいイベントから順にすべて取る (ポイントが 0 のルームの分は取らない)。累計ランキングの値はルームごとにおよそ月 1 回残し、ギフターの月ごとの支出の推移 (ギフターのページの「支出の移り変わり」) に使う。30 日以内に配信したルームは 1 週間ごとに取り直す。集めた情報は `state/research.db` (SQLite。古いイベントの貢献ランキングまで集めると数 GB、約 5,000 万行になる見込み。全部集め終わるまで 0.5 秒に 1 回 (`SHOWROOM_RESEARCH_GAP`) で 1 か月ほど) |
| `SHOWROOM_RESEARCH_SCAN` | 上と一緒に、ルーム番号を 1 から順に 1 回だけ調べて、配信もイベント参加もしていないルームも見つける (既定 `true`。約 58 万回、ほかの収集と順番に行うので 1〜4 週間)。フォロワー 0 人のルームは調べない |
| `SHOWROOM_RESEARCH_ARCHIVE` | 上と一緒に、Internet Archive (web.archive.org) に残っている古いイベントのページ・貢献ランキングのページから、消えたルームと、退会したユーザーの前の名前を取り戻す (既定 `true`。SHOWROOM には問い合わせず、Internet Archive に 6 秒に 1 回 (`SHOWROOM_RESEARCH_ARCHIVE_GAP`)。数日かかる) |
| `SHOWROOM_RESEARCH_GAP` | SHOWROOM への問い合わせの間隔 (秒、既定 `0.5`)。指定のルームの収集と全ルームの収集を合わせてこの間隔。混んでいる・止められている (403・429・5xx・通信の失敗) ときは自動で倍ずつ広げ (最大 60 秒)、5 回続けて失敗したら止める。止める時間は 1 時間・2 時間・4 時間… と続けて止めるたびに倍にし (最大 24 時間)、再開後 200 回続けて成功したら 1 時間に戻す。止めている時は管理画面の上に出る (視聴とログインの維持は止めない) |
| `SHOWROOM_HEADLESS` | `false` で画面表示 |
| `SHOWROOM_STATE_FILE` | セッション保存先 |
| `SHOWROOM_BROWSER_CHANNEL` | 使用ブラウザ (`chrome` / `msedge` / 空で付属 Chromium) |
| `SHOWROOM_BROWSER_EXECUTABLE` | 使用するブラウザ実行ファイルのパス |
| `SHOWROOM_PROXY` (または `HTTPS_PROXY`) | ブラウザが使うプロキシ |
| `SHOWROOM_VIDEO_QUALITY` | 視聴する画質 (`low` 256x144・約 0.2Mbps / `medium` 640x360・約 0.8Mbps / `original` 配信そのまま・最大 1080p 約 6Mbps / `auto` 再生プレーヤー任せ)。既定は `medium` (再生枠と同じ大きさで、1080p の配信でも映像の処理が軽い。`low` は通信量は最少だが引き伸ばして描くため CPU はかえって増える)。SHOWROOM の再生プレーヤーで選べる画質と同じもの |
| `SHOWROOM_GIFT_UPDATE_DAYS` / `SHOWROOM_GIFT_UPDATE_TIMES` | ギフトの一覧 (名前・ポイント) を SHOWROOM から取り直す曜日と時刻 (日本時間)。既定は毎週月曜日の `0:00,3:00,12:00,15:00,18:00`。起動時にも取り直し、止めていた間に予定の時刻を過ぎた時も、次に使う時に取り直す。新しいギフトとポイントが変わったギフトはログに出る |
| `SHOWROOM_BACKGROUND_TABS` | 配信ページを空白のページの裏 (背面のタブ) に開く (既定 `true`)。映像の再生・コメントの受信と投稿はそのままで、画面の描き直しが減り CPU が約 3 割減る |
| `SHOWROOM_KEEP_OPEN_WHEN_OFFLINE` | 配信していないルームのページも開いておくか (`true` / `false` / `auto`。既定は `auto` でメモリを見て決める) |
| `SHOWROOM_WEB_PORT` / `SHOWROOM_WEB_HOST` | 管理画面のポート (既定 8080、0 で無効) と待ち受けアドレス (既定 127.0.0.1) |
| `SHOWROOM_WEB_PASSWORD` | 管理画面のパスワード。設定すると localhost 以外からも開ける |

## トラブルシューティング

| ログ | 原因と対処 |
| --- | --- |
| `このルームは視聴できません` | 年齢制限付きルームなど、未ログインでは見られないルームです。`login` でログインしてください |
| `再生が進んでいません` が続きリロードを繰り返す | Chrome ではなく付属 Chromium で起動している (起動時の警告を確認)、または回線が WebRTC (UDP) を通さない可能性があります |
| `Intel 版 Python (Rosetta 2) で動いています` | Apple Silicon の Mac で Intel 版 Python を使っていると Chrome も Intel 版で動き非常に遅くなります。`rm -rf .venv && arch -arm64 /usr/bin/python3 -m venv .venv` で作り直し、再度 `pip install -r requirements.txt` してください |
| ページの読み込みが異常に遅い | `python -m showroom_keeper diagnose` で、どの通信が遅いかを計測できます |
| `未ログインです` | 保存したセッションの期限切れです。`login` をやり直すか、ID/パスワードを設定してください |

## 構成

```
showroom_keeper/
  cli.py       コマンドライン (run / login / comment / status / gifts / diagnose)
  config.py    設定ファイル・環境変数の読み込み
  api.py       SHOWROOM API (配信状態・ログイン状態・ログイン)
  watcher.py   1 ルーム分の監視ループ (配信待機・再生監視・リロード・バックオフ・ギフト記録)
  keeper.py    ブラウザ管理・セッション保存・全ウォッチャーの統括
  comments.py  手動コメントの受け渡し (comment コマンド ⇔ 常駐中の keeper)
  status.py    配信状況の取得と表示 (status コマンド)
  activity.py  リアルタイム通信の読み取りと推定アクティブ人数
  gifts.py     ギフト履歴の記録と集計 (gifts コマンド)
  entrance.py  配信開始時に一度だけ入室する (enter_rooms)
  recorder.py  ブラウザを使わないギフト記録 (record_rooms / events)
  web.py       管理画面のサーバー (標準ライブラリのみ。run と同じプロセスで動く)
  admin.html   管理画面 (1 ファイルで完結し、外部のライブラリや CDN を読み込まない)
deploy/        サーバー用スクリプト (setup-server.sh / comment.sh / status.sh / gifts.sh) と systemd ユニット例
tests/         pytest によるテスト
```

## 注意事項

- `.env`、`config.yaml`、`state/` (セッション Cookie) には認証情報が含まれます。`.gitignore` 済みですが、共有しないでください。保存したセッションファイルは権限 600 で書き出します。
- 映像は WebRTC (UDP) で受信します。UDP を遮断するネットワークやプロキシ経由では映像を受信できません。
- SHOWROOM の非公式 API・ページ構造に依存しているため、サイト側の仕様変更で動かなくなる可能性があります。
- SHOWROOM の利用規約を確認のうえ、自己責任で利用してください。
