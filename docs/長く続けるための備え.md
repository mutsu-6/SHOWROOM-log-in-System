# 長く続けるための備え (20 年続ける前提)

2026-10-18 に利用者が「形が完成したら 20 年は続ける」と決めた。そのために、止まる前に気づくこと・
壊れても戻せること・古くならないことを、ここにまとめる。サーバーの守りは Cursor の受け持ち (`AGENTS.md`)。

## 自動で行っていること
| 何を | どのように | どこで確かめるか |
|---|---|---|
| 新しい版を入れる | 自動テストが通ってから 10 分ほどで入る (`tools/auto-update.sh`、5 分ごと) | 管理画面「収集」の「動いている版」 |
| 作り直しのファイルの片付け | 更新のあとに、作り直しのファイルを 5GB までに減らし、使っていないイメージを消す (`tools/update.sh`) | `sudo docker system df` |
| research.db の写し | 毎日 4:00 に `data/backup/` に、gzip で縮めて 1 つ作る (`research-YYYYMMDD-HHMM.db.gz`。半分ほどの大きさ)。空きが足りない時は、前の写しを消してから作り、それでも足りなければ作らない | 「収集」のバックアップの行 |
| ディスク全体の写し (スナップショット) | Google Cloud が毎日 1:00 (日本時間) に作り、14 日分残す。ディスクを消しても残る (今は officea-prod の中。下の「置き場所」を参照) | Google Cloud のコンソール |
| 終わったイベントの推移の間引き | 終わって 7 日たったイベントは、分析に使う回だけ残す | — |
| OS のセキュリティの更新 | Ubuntu の自動の更新 (unattended-upgrades) | — |

## 赤い帯で知らせること (管理画面のいちばん上)
- ログインが切れた・ログインの確認が途絶えた
- ディスクの空きが 4GB より少ない・このままだと 180 日以内にいっぱいになる (research.db・gifts・live_events・backup の大きさと、research.db の表ごとの大きさ (毎朝のバックアップの写しで測る) も毎日残し、いちばん増えているものを出す)
- 貢献ランキングを取り終わるまでに使う見込みが、収集を止めるまでの空きの 7 割を超えた (取り終わるまでの残りの件数 × 1 件の大きさ。ここ数日の増え方とは別に見積もる)
- research.db の写しに失敗した・2 日以上作られていない・サーバーの外に送れなかった
- 全ルームの収集が 1 時間以上進まない
- SHOWROOM への問い合わせが 24 時間に 3 回以上止められた (SHOWROOM の仕組みが変わったか、断られている)

赤い帯は、管理画面が開ける時にしか見えない。サーバーそのものが止まった時は、まだ知らせられない (下の「残っていること」)。

## 決まった時期にやること
### 毎月
- 管理画面を開き、赤い帯が出ていないか・「動いている版」が最新かを見る
- ディスクの増え方を見る (下の「ディスクを長く持たせる」)
- `docs/残っている作業.md` を見直す

### 毎年 (10 月ごろ)
- 写しから本当に戻せるかを試す (下の「写しから戻す」を、試し用の場所で行う)
- 視聴に使うブラウザの部品 (`Dockerfile` の Playwright の版) を新しくする。古いままだと SHOWROOM が動かなくなることがある
- Python と部品 (`pyproject.toml`) の版を新しくし、自動テストで確かめる (自動テストは Python 3.9 と 3.13)
- ディスクの増え方を見て、足りなくなる前にディスクを広げるか、古い記録をまとめる
- 支払いのカードの期限・Google と GitHub のアカウント・パスワードの置き場所を確かめる

### 5 年ごと
- サーバーの OS を新しくする。今の Ubuntu 24.04 は、通常の更新が 2029 年に終わる
  (新しいサーバーを作って写しを移し、動いたら切り替える。上書きで上げない)
- サーバーの大きさ (今は e2-small、メモリ 2GB) が足りているかを見直す

## 写しから戻す (research.db が壊れた時)
サーバーで行う。視聴は数分止まる。
```bash
cd ~/SHOWROOM-log-in-System
sudo docker compose stop
sudo ls -la data/backup/                      # research-YYYYMMDD-HHMM.db.gz (縮めた写し) を確かめる
sudo mv data/research.db data/research.db.broken
sudo rm -f data/research.db-wal data/research.db-shm
sudo sh -c 'gunzip -c data/backup/research-YYYYMMDD-HHMM.db.gz > data/research.db'
sudo docker compose up -d
```
- 写しを作った時刻よりあとに集めた分は失われる (次の収集でまた集める)。
- 戻すには、research.db の大きさの空きが要る。足りない時は、壊れた `research.db.broken` を先に消す (ほかの写しがあることを確かめてから)。
- 2026-10-21 より前に作った写しは縮めていない (`.db`)。その時は `cp` で戻す。
- 前の日に戻したい時・サーバーの中の写しも壊れた時は、Google Cloud のディスクの写し (14 日分) から、新しいディスクを作って research.db を取り出す。

## 置き場所 (いちばん大きな心配)
サーバー (`instance-20261014-163017`) は、Google Cloud の `officea-prod` プロジェクトの中にある。
officea はこのシステムとは全く別のプロジェクトで、閉じたり、支払いや権限が変わったりすると、このシステムも一緒に止まる。
毎日のディスクの写しも同じプロジェクトの中にある。

- officea のもの (バケット・データベースなど) には触れない。サーバーの権限を広げると officea のものにも届くので、広げない
- サーバーは officea と同じ標準のアカウント (プロジェクトの編集者) で動くので、2026-10-22 にサーバーの権限から Cloud Storage を外した
  (ログと見張りの書き込みだけが残る)。officea のバケットは読めない (403)。このシステムは Cloud Storage を使っていないので、働きは変わらない。
  サーバーの外の写し (`SHOWROOM_RESEARCH_BACKUP_GCS`) は、引っ越したあとの専用のプロジェクトで、専用のアカウントに権限を付けて使う
- ネットワークは officea と分かれている (このシステムは `default`、officea は別のネットワークで、つなぐ設定は無い)
- サーバーを止めて設定を変える時は、先に `docker compose stop` をした場合、起動したあとに `sudo docker compose start` が要る
  (手で止めたものは自動で起動しない)
- 20 年続けるなら、このシステム専用のプロジェクトに引っ越す。引っ越しの流れ:
  1. 利用者が専用のプロジェクトを作り、支払いを付ける
  2. 新しいプロジェクトにサーバー (Ubuntu の LTS) を作り、Docker を入れ、リポジトリを置く
  3. 古いサーバーの `data/` (research.db・gifts・ログイン状態) と `.env` を移す (秘密の情報なので、利用者の手元を通さず、サーバーからサーバーへ移す)
  4. 新しいサーバーで起動し、ログイン・視聴・収集が動くのを確かめる
  5. 古いサーバーを止める (すぐには消さず、しばらく残す)
  6. 専用のバケットに外の写しを送る (`SHOWROOM_RESEARCH_BACKUP_GCS`)

## ディスクを長く持たせる (2026-10-21 に利用者と決めた)
ディスクを大きくするのは、下の工夫をしても足りない時だけにする。何も消さずに記録が増え続けるので、決まった時期に見直す。

| 段 | 何をするか | 状態 |
|---|---|---|
| 1. 無駄を減らす (データは消えない) | 写しを縮めて 1 つにする (古い日はディスクの写しで戻す)・縮める間に、縮め終えた所から一時の写しのディスクを返す (要る空きが DB の 1.8 倍 → 1.2 倍) | 入れた |
| | イメージを使うブラウザだけにする (4.7GB → 1.5GB ほど)・snap の古い版と apt の残りを消す (snap は 2 版まで残す設定にした) | 入れた |
| | イベントのページの文 (`event_pages`) を縮めて保存する・`user_room_scan` の索引が要るかを見直す | Claude Code に頼む |
| 2. 先を見張って自動で守る | 「いっぱいになる日」(30 日の減り方) と「取り終わるまでに使う見込み」を赤い帯で知らせる。写しは空きが足りなければ前の写しを消し、それでも足りなければ休む。空き 2GB で全ルームの収集を止める (`sweep.DISK_MIN`) | 入れた |
| 3. 古い記録をしまう | 取り終わったあと 2 週間ほどふだんの増え方を測り、古い月の分を縮めて別のファイルにしまう形を Claude Code と決める | 測ってから |

2026-10-21 に測ったこと:
- 30GB のうち 19GB を使用。Docker 7.9GB・サーバーの中の写し 2.4GB・research.db 2.1GB・OS など 4GB ほど
- research.db はページの隙間が 0〜16% で、無駄は少ない。1 日 +0.5〜0.7GB のほとんどは、貢献ランキング (`contributions`) と `user_room`
- 貢献ランキングはまだ 72% (52.5 万件) を取っていない。取り終わるまでに DB は 2.5GB ほど増える見込み (1 件 4〜5KB)
- 写しを縮めると: gzip -1 で半分ほど (300MB が 55 秒)。zstd でも 2.2〜2.9 分の 1 で、大きくは変わらない

毎月の見直し (「決まった時期にやること」の毎月に足す): 管理画面の赤い帯と、`data/disk_history.json` の表ごとの増え方を見る。

## 残っていること
- 専用のプロジェクトへの引っ越し (利用者がプロジェクトを作ってから)
- サーバーの外の写し (引っ越しのあと、専用のバケットで)
- サーバーそのものが止まった時に、外からメールで知らせる (Google Cloud の無料の見張り。送り先のメールアドレスが要る)
- データの増え方をはかり、20 年分が収まる決まりを作る (グリッターのルームの記録を始めたので、gifts フォルダの増え方を見る)
