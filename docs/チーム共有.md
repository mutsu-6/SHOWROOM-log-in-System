# SHOWROOM Analytics — チーム共有・立ち上げ資料

作成: 2026-10-20 (日本時間)。Codex が下書きし、Claude Code が PR #73 までに合わせて直した (確認基準: `fcd9a28`)。
Claude Code・Cursor・Codex・Gemini が、同じ前提で作業を始めるための資料です。
新しい作業では最新のコミットと報告を読み、この時点からの差分を確認してください。

## 最初に知ること

SHOWROOM のルーム・イベント・ギフト・ランキングを集め、ギフターの動きやイベントの作戦を考えるシステムです。
ログインを維持して視聴する機能も同じプロセスで動きます。最優先はギフターの分析。
収集・分析が、視聴とログイン維持を妨げないようにします。

- 名前は **SHOWROOM Analytics**。`showroom_keeper` や `SHOWROOM_` などの内部名は従来のままです。
- リポジトリ: `mutsu-6/SHOWROOM-log-in-System`。
- 統合先・PR の送り先: `claude/showroom-login-persistence-gfdxzo`。作業を始める前に現在のブランチと差分を確認します。
- 全員の方針と担当の基準は [AGENTS.md](../AGENTS.md)。この資料はその案内と補足です。
- 本番は e2-small・メモリ 2GB。クラウドの開発環境とは資源もデータ量も違います。
- 秘密の情報や、実在のギフターの名前・ID は、公開リポジトリ、報告、PR に書きません。

## 利用者 (M) との進め方

利用者がこれまでに決めた、全員に共通の進め方です。

- **サーバーでの作業は Cursor に頼む。** 測る・確かめる・`.env` を変えて起動し直す、などの手順を利用者に渡さない。
  ほかの AI がサーバーでの確認を必要とする時は、Cursor にそのまま貼れる依頼文を書く (利用者: 「私ではなく Cursor に作業を依頼せよ」)。
  本番サーバーに入るのは Cursor だけ。Codex・Gemini は本番につながない
- **重くしない・遅くしない。** 機能を足す時は、サーバーが重くならない方法を選ぶ。管理画面のページを開く速さを遅くする変更は入れない。
  遅い処理・重い処理もバグとして扱う
- **作業を始める時に、作業の範囲を [作業中.md](作業中.md) に書く。** だれが・何のために・どのファイルを直すかを書いて、すぐ作業ブランチに入れる
  (ほかの AI が `git pull` で見られるように)。終わったら自分の行を消す。始める前に、ほかの人の行と同じファイルを直さないかを見る (2026-10-22 に利用者が決めた)
- **ほかの AI と作業がぶつからなければ、自分でマージしてよい (2026-10-22 に利用者が決めた)。** ぶつからないとは、[作業中.md](作業中.md) と
  開いているプルリクエストに、同じファイルを直す人がいないこと。ぶつかる時は、相手の人と利用者に伝えて待つ。
  マージすると、10 分ほどでサーバーに自動で入り、そのたびに起動し直して視聴が 1〜2 分途切れる。なので、プログラムの変更のマージは
  なるべくまとめ、視聴が大事な時間を避ける (説明書だけの変更はサーバーを起動し直さない)。自動テストが通ってからマージする
- **できる作業が無い時は、待たずに止めて報告する。** 何かが終わるのを待つだけの時間を作らない。待つ間にできる作業があれば先にし、
  無ければその時点で作業を止め、何を待っているか・いつ確かめられるかを報告する (2026-10-22 に利用者が決めた)
- **測り直しを待って止まらない。** 今ある Cursor の数字で始められる時は始め、Cursor に確かめてほしいことを並べて渡す
- **分析の提案は、イベントの戦い方まで考えてから出す。** 数字を分けるだけの案は「考察が浅い」と言われた (2026-10-20)
- **報告の置き場所と名前**: `docs/報告/<名前>の作業_<日付>.md` (例: `Cursorの作業_2026-10-19.md`・`Codexの作業_2026-10-20.md`・`Geminiの作業_2026-10-20.md`)。
  ブランチは `cursor/…`・`codex/…`・`gemini/…`・`claude/…` のように名前で始め、プルリクエストは作業ブランチ `claude/showroom-login-persistence-gfdxzo` に向ける
- **ほかの人の受け持ちの直しを見つけた時**は、自分で直さず、報告に「どのファイルの何行目を、なぜ、どう直すとよいか」を書く。
  受け持ちの人が直す。Cursor が Claude Code のプルリクエストを見る時と同じやり方
- 利用者は AI どうしの文書を貼り合わせて渡すことが多い。利用者がそのまま貼れるよう、最後に「◯◯への報告」をまとめて書くとよい

## 設計と分析で守る前提

- 収集の問い合わせは `research.THROTTLE` を通し、既定 `research_gap=0.5` 秒。視聴・ログイン維持・入室はそれぞれの間隔で動きます。
- ログイン確認はアカウント単位で、既定 7200 秒に一つのルームで行います。
- Docker の設定は `.env` の `SHOWROOM_...`。Docker は `config.yaml` を読みません。
- 大きな SQLite の表を読む処理では、実行計画と読む量を確認します。対象の回帰確認は `tests/test_query_plans.py` にあります。
- `memory.heavy` は重い集計の重なりを抑えます。`once.shared` は同じ要求の計算を共有し、`room_parts` は画面用の部品を保存します。
- 累計ランキングは上位30人、イベントの貢献ランキングは上位100人まで。未観測・未収集はゼロではありません。
- 「戦力」の予算・残りは観測ポイントから作る目安です。本人の資産や支払い能力を直接示す数字ではありません。
- 試験段階でできることを試す方針を維持し、利用者が決めた機能を勝手に削除・縮小しません。

### 予測と順位の 3 つの決まり (2026-10-26 に利用者が決めた)
「1 イベントだけ爆投げしたギフターが見込み量の 1 位になっている」から。採点で弱点が分かっていたのに、画面の順位をそのままにしていたため。
1. 順位や予測を出す画面には、必ず「何回分のデータか」と「信頼度」を付ける (戦力ランキングの「信頼度」の線は `docs/分析の見方.md`)
2. 予測の式を変える・足す時は、採点の道具 (`backtest.py`、写しで動かす) で「何も考えない予測」に勝つことを、マージの条件にする
3. マージの前に、出来上がった上から 10 人を目で見て、1 回だけの人やデータの穴が上に来ていないかを確かめる (名前・ID はファイルや PR に書かない)

## 開発環境を立ち上げる

### 全員共通

既存のチェックアウトを使い、ブランチ・`git status --short`・対象コミットを確認します。
相手の新しい変更を読み、作業ブランチの変更を取り込みます。手元の変更を上書きしません。
Codex のクラウドタスクは隔離済みなので、利用者が明示的に求めない限り追加の Git worktree は作りません。

依存関係がまだなければ、リポジトリ直下で次を実行します。Python は3.9以上、CI は3.9と3.13です。

```bash
python -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pip check
.venv/bin/python -m pytest -q
```

上は POSIX 環境の例です。Windows では仮想環境の `Scripts/python.exe` に読み替えます。
ブラウザ視聴には Google Chrome を推奨します。テストを動かすことと、実サイトの映像を再生することは別の確認です。
ログインが必要な作業は、既存の接続や環境変数の有無を値を出さずに確認します。秘密の値を会話で求めません。

| Python | 3.12、リポジトリ内の `.venv` |
| Chrome | `/workspace/.onboarding/chrome/opt/google/chrome/chrome` |

同じクラウドで設定ファイルが存在する場合の起動:

```bash
cd /workspace/SHOWROOM-log-in-System
.venv/bin/python -m showroom_keeper -c /workspace/.onboarding/showroom-dev.yaml run
```

二重起動を避け、長時間実行用のセッションで動かします。停止は Ctrl+C または SIGTERM。
内部確認では `GET http://127.0.0.1:8080/` が200で `SHOWROOM Analytics` を含み、
`GET http://127.0.0.1:8080/api/health` が200の JSON を返すことを見ます。
このクラウドの localhost のプレビューリンクは作りません。
環境設定にインストール手順・起動手順・必要な通信先の案は保存済みですが、公開や新しいタスクでの復元まで確認したとは扱いません。
通信先を反映した後は、実際のリクエストとアプリのログで再確認します。

本番の更新が必要な仕事では、[サーバーの更新](サーバーの更新.md) に従います。
サーバー側は `bash tools/update.sh`、Mac 側は「サーバーを更新する.command」を使います。
Git の取り込み・環境設定の保存・本番での起動成功をそれぞれ区別して報告してください。

## 作業を受け渡す形式

各 AI の会話や記憶は自動共有されません。Git に保存しても、相手が読んだことまでは確認できません。
報告を `docs/報告/` に保存し、利用者や次の担当へブランチ・ファイル・対象コミットを渡します。
必要に応じて次の形を使ってください。秘密の情報や実在のギフターの識別情報は含めません。

```text
担当・日付 (日本時間):
目的・利用者からの依頼:
対象コミット・作業ブランチ:
読む資料・変更するファイル:
確認できた事実と根拠 (コード/テスト/実測の別):
変更内容、または提案:
検証したコマンド・結果 (成功/失敗/未実行):
未確認・残っている課題:
次の作業と引き継ぎ先:
```

## Gemini に最初に渡す文

下をそのまま渡せます。リポジトリを読めないチャットで使う場合は、`GEMINI.md`・`AGENTS.md`・この共有資料の三つを添付します。
添付だけで最新コードまで確認したことにはなりません。追加の資料が必要なら対象のファイル名を挙げてもらいます。

```text
あなたは SHOWROOM Analytics の開発メンバー Gemini です。
Claude Code・Cursor・Codex と協力します。説明は日本語でお願いします。

最初に GEMINI.md、AGENTS.md、docs/チーム共有.md を読み、現在のコミットと最新報告を確認してください。
初期の協力範囲は、資料とコードをまたぐレビュー、分析の仮説と検証方法、説明の見直しです。

最初の仕事は、PR #72 で入った「ギフターのステータスと戦力ランキング」(showroom_keeper/gifter_status.py・

説明が利用者に分かりやすいかを見ることです。仮説・根拠・検証方法・負荷への影響を添えてください。
結果は docs/報告/Geminiの作業_<日付>.md に書きます。
本番には接続せず、コード変更はせずに、まずレビュー結果を共有してください。
資料だけが渡されている場合は、その範囲で検討し、確認に必要なコードや報告を列挙してください。
```
