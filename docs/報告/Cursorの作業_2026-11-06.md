注意:
- research.db は `auto_vacuum` が 0 なので、A〜D で表を作り直しても**ファイルは小さくならない**。空いた所 (A〜D で約 1.0GB) は、そのあと増える分 (1 日 130MB) に 8 日ほど使われる。ファイルそのものを小さくするのは E だけ。
- F・G は、読む所 (`explore.update_gift_senders`・`update_gift_events` などは、ルームごとに「どこまで読んだか」を覚え、**ファイルが小さくなるとそのルームを最初から作り直す**) が .gz を読み、しまったファイルを「小さくなった」と見ないようにしてからでないと、作った表の中身が消える。

## 5. 効く順 (Cursor の考え)
1. **F・G (ギフトと live_events の古い日を gzip に)**: ディスクがすぐ 1.4GB 空き、毎日の増え方も 1/3 ほど減る。いちばん効く
2. **B' (gift_events の作り直し)**: −413MB と、research.db の毎日の増え方 (130MB) のうち約 25MB を減らす
3. **A (contributions)**: −578MB。今は増え方が小さいので、一度きりの効き目
4. C・D: 小さいが、手間も小さい
5. E: A〜D のあとにまとめて 1 回 (収集を止めて行う。利用者と時刻を決めて)

## 6. Claude Code へのお願い (受け持ちのファイルのため、Cursor は直していない)
- 上の F・G のために、ギフトと live_events の記録を読む所 (explore・listing・gifts.load_recorded・stage_ranks・event_analysis・research_store の room_gift_daily) が、`<名前>.jsonl.gz` (しまった分) と `<名前>.jsonl` (書いている分) を続けて読めるようにする。しまう仕事 (日付が変わって 2 日たったファイルを gzip にする) をどこに置くかも決めてほしい (Cursor が書いてもよい)
- A・B'・C・D の表の作り直し。サーバーはメモリ 2GB なので、shrink.py と同じように、裏の仕事で少しずつ (作り直しの間は、新しい表の分の空きが要る。A は約 1.4GB、B' は約 0.3GB)
- 新しい表を作る時の決まりを `docs/長く続けるための備え.md` に書いた (大きな表は WITHOUT ROWID・文字のキーは番号に・先頭が同じ索引を作らない)
