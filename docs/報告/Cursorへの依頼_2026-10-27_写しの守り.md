# Cursor への依頼: 写しを作る前に前の写しを消さない (2026-10-27、Claude Code から)

M さんが 10-27 に「進めて」と決めた (全体の見直しの ①)。`showroom_keeper/backup.py` は Cursor の受け持ちなので、直しをお願いします。
ギフターの名前・ID は書かないでください。結果は `docs/報告/Cursorの作業_<日付>.md` に。

## 何が起きているか (06fdf55 で読んだ)

- `backup.py:136-137`: 写しを 1 つだけ残す決まり (`KEEP = 1`) で、`copies(state_dir)[max(keep - 1, 0):]` は全部の写しになる。
  **新しい写しを作り始める前に、残している写しを全部消している**
- 写しを作るのに 1,480 秒かかる (10-25 4:00、Cursor の 10-26 の報告)。だから毎朝 4:00〜4:25 は、サーバーの中に写しが 1 つも無い。
  この間に作るのに失敗すると (メモリ・ディスク・起動し直し)、次の朝まで写しが無い
- 要る空きは「research.db の大きさ × 1.2 + 1GB」(`backup.py:117-120`)。前の写しを消したあとの空きでくらべると、
  research.db が 7〜7.5GB で毎朝失敗し始める見込み (Claude の推測。11 月 3〜5 日ごろ)。その時、前の写しはもう消えている
- 写しには、SHOWROOM から取り直せないデータ (`gift_events`・`event_progress`・`event_final`・`room_lives`・`room_daily`・来場の記録) が入っている

## 直してほしいこと

1. **新しい写しができてから、前の写しを消す**。空きが足りなくて新しい写しを作れない日は、前の写しを消さずに残し、管理画面の「収集」に「作れなかった」と出す
   (今は空きが足りない時に前の写しを消してから作り直そうとする。`backup.py:139-144`。消したうえで作れなかった時に、写しが 0 になる)
2. できれば: **取り直せない表だけの小さな写し** も毎朝作る (上の表だけなら数百 MB の見込み)。研究の DB 全体より小さいので、空きが少ない日でも作れる。
   サーバーの外に置くかは、M さんがまだ決めていない (全体の見直しの 6 章の 2)
3. 直したら、次の朝の写しで `last.json` の ok・seconds・mb と、作っている間に前の写しが残っていたかを確かめる
