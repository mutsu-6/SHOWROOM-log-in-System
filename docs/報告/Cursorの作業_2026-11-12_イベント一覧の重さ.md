# Cursor の作業 2026-11-12: イベントの一覧を開くのが重い

利用者の画面は、イベントの「開催中」が「読み込み中」のまま止まっていた。

## 原因

一覧の API (`/api/events`) が、出すイベントごとに次をその場で数えていた。

- 参加ルームの数、貢献ランキングを取り終えた数、1 位のルーム (`room_events`)
- 推移を残した回数 (`event_progress` の時刻を全部見る)
- 開催中は、それに加えて API の遅れ。記録しているルームの直近 7 日のファイルを全部読む (2026-10-19 の測定では 11 秒。ファイルが増えるとさらにかかる)

推移の表は大きい。遅れのファイル読みと重なると、ページを開いたまま返ってこない。

## 直したこと

一覧は `events` に保存してある数字だけを読む。

- 参加ルームの数は、もともと保存している `room_count`
- 1 位は `leader_room_id` (参加ルームを保存するときに入れる)
- 推移の回数は `progress_n` (推移を 1 回残すたびに増やす。最初の 1 回とそのイベントを間引くときだけ数える)
- 貢献ランキングの件数は `ranking_count` (貢献ランキングを保存するときに、そのイベントだけ数える)

まだ数字の無いイベントは、収集の合間に 1 件ずつ、終わりの新しい順に数える。ページを開いたときには数えない。

API の遅れも、一覧では保存してある分だけ出す。計算は収集が 1 時間に 1 回行う。計算し終えるまでは、一覧の説明は「まだ測っていません」の文になる。

この環境で、開催中 40 件・推移 48 万行のデータベースに、前の問い合わせをかけたところ 0.024 秒だった。本番は表もディスクもこれより重いので、一覧からはその表を読まないようにした。
