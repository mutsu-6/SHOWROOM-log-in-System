# Cursor への依頼: ディスクの増え方を測る (2026-10-26、Claude Code から)

管理画面に「このままだと、ディスクがあと 28 日ほどでいっぱいになります (空き 11.3GB。いちばん増えているのは research.db (1 日 約 546MB))」と出ています。
何が増えているのかを決めてから直したいので、次を **読むだけで** 測ってください (書き換え・消す・止めるはしない)。
重い処理 (動いている research.db に dbstat・VACUUM・全部を数える SQL) はしないでください。表ごとの大きさは、毎朝のバックアップが写しで測って残しているものを読みます。
ギフターの名前・ID は出さないでください。結果は `docs/報告/Cursorの作業_<日付>.md` に書いてください。

## Claude Code の見立て (確かめたいこと)
1. 増えているのは、ほとんどが過去のイベントの貢献ランキングを取り込んでいる分 (`contributions`・`user_room`・`user_month`・`room_events`) ではないか。
   10-21 の測りでは「まだ 72% (52.5 万件) を取っていない。取り終わるまでに約 2.5GB」だった。取り終われば増え方は大きく下がるはずで、
   「28 日」は今の増え方がずっと続く前提の数字。取り終わるまでの残りが分かれば、本当にいっぱいになるかが決まる
2. サーバーの `user_room` が古い形 (WITHOUT ROWID でない) のままで、`user_room_scan` という、表とほぼ同じ中身の索引を別に持っているのではないか。
   そうなら `user_room` は同じ中身を 3〜4 回持っていることになり、形を作り直すと何百 MB か減る見込み
3. 「1 日 546MB」には research.db-wal (書き込み待ち。バックアップ中は 444MB までふくらんだ) が入っているので、本体の増え方より大きく見えているかもしれない

## 測ってほしいこと
1. ディスク全体: `df -h /`、`sudo docker system df`
2. data フォルダの中の大きさ: `research.db`・`research.db-wal`・`backup`・`gifts`・`live_events`・`comment_counts`・`cache` (`du -sh`)
3. `data/disk_history.json` の、直近 14 日の「日時・空き (GB)・research.db・backup・gifts の大きさ」の表
4. 表ごとの 1 日あたりの増え方 上位 15 (コンテナの中で `backup.growth(Path('/data'), time.time())`。MB にして)
5. 最後のバックアップの記録 (`backup.last_backup(Path('/data'))`) の `mb`・`raw_mb` と、`tables` の大きい順 上位 15 (MB)
6. 貢献ランキングの残り: `backup.backlog(Path('/data'))` の結果 (`pending`・`per_ranking`・`bytes`)。
   それと `meta` の `coverage_cache` の、月ごとの `done`・`pending` の合計
7. `user_room` の形: `SELECT name, sql FROM sqlite_master WHERE tbl_name='user_room'` (読み取り専用でつなぐ。中身は読まない)
8. 写しの数と大きさ: `data/backup` の中のファイルの一覧と大きさ

## そのあと (Claude Code が直す候補。数字を見てから、利用者に聞いて決める)
- 2 が当たっていれば: `user_room` を WITHOUT ROWID の形に作り直す (一度だけ。時間と空きが要るので、やり方は数字を見て決める)
- イベントのページの文 (`event_pages`) を縮めて保存する (10-21 の「ディスクを長く持たせる」で頼まれていたもの)
- 取り終わったあとも 1 日 200MB 以上増えるなら、「古い記録をしまう」(長く続けるための備え.md の 3 段目) を前倒しで決める
- それでも足りなければ、このサーバーのディスクを広げる (利用者に聞く)
