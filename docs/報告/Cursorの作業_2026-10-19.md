## 直したこと: ギフターの一覧で期間を決めた時 ([PR #33](https://github.com/mutsu-6/SHOWROOM-log-in-System/pull/33))

### 困っていたこと
- ギフターの一覧で「直近 7 日」などの期間を決めると、その間に送りのあったルームの記録のファイルを読んでいた。
- 今の記録は一番古いもので 4.2 日前なので、7 日以内に送りのあるルームは 816 ルーム全部。毎回 70MB のファイルを読み、41〜87 秒かかり、メモリが 520MB 以上増えていた。2GB のサーバーでは、ほかの処理 (視聴・ログインの維持) を止めかねない量。
- 記録がたまっても、7 日以内に送りのあるルームはほぼ全部なので、変わらない。

### 直し方
- 期間を決めた時は、ギフト 1 件ずつの表 (`gift_events`。3a8c2ee で Claude Code が作ったもの) から、人 × ルームの合計を SQL で出す。ポイントは、ギフトの一覧を一時表に入れて SQL の中で数える。
- 表に足し終えていないルームだけ、これまでどおりファイルを読む。
- 個数 (count) も出るようになった。名前は、その期間に使った名前から出す。
- 「すべての期間」と、ルームを 1 つに絞った時は、前のまま。

### 結果 (サーバーに入ったあと。版 0c3bb01)

| 一覧 | 前 | 今 |
|---|---|---|
| 直近 7 日 (1 回目) | 41〜87 秒・メモリ +520〜545MB | 16.8 秒・+85MB |
| 直近 7 日 (2 回目) | 41 秒 | 14.3 秒・+116MB |
| すべての期間 (参考。変えていない) | 6〜7 秒 | 7.5 秒 |

- 答え合わせ: 前の作りと今の作りで「直近 7 日」を出し、上位 3 人のポイント・個数・ルームの数が同じだった。全員の合計 (約 3,126 万 pt・約 53.8 万回) は 0.005% ずれたが、これは 2 つを測る間に新しく送られたギフトの分。
- 今の 16 秒の内わけ: SQL が約 8 秒、ギフトの一覧の取り直し (SHOWROOM への問い合わせ) が約 2 秒、一覧の組み立てが約 3 秒。

### テストで見つけたこと (Claude Code に伝えたい)
- `tests/test_query_plans.py` の `full_scans` は、別の接続で読み方 (EXPLAIN QUERY PLAN) を確かめる。そのため、一時表を使う SQL は「表が無い」エラーになり、**黙って飛ばされる**。
- 今回の SQL も、はじめは SQLite が `gift_events` を全部読む読み方を選んでいたのに、テストは通っていた。`CROSS JOIN` で読む順番を決め、テストの中で一時表を作って読み方を確かめるようにした。
- Claude Code の `_sender_rooms` の `sender_done` を使う SQL も、同じ理由でまだ確かめられていない。

- ディスクは **pd-balanced (SSD の一種)・30GB**。「標準」(回転するディスク) ではない。
- キャッシュを通さずに読む速さ: 飛び飛びの 4KB は中央 0.52ms (遅い 1 割 0.73ms・最大 192ms)、1 本で平均 490 回/秒。続けて読むと 128MB/秒。
