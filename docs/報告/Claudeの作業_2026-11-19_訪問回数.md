## 1. コードで確認できたこと

### 今の入室は、配信ごとに同じ訪問者のまま live_info を 1 回呼ぶか → 呼ぶ (うまくいく時)

`2577cb5` の `showroom_keeper/entrance.py`:

- `_due` (191 行目あたり): 入室済みの `live_id` と違う配信だけを入室の対象にする。同じ配信には 2 回入らない。
- `_greet` (252〜271 行目): 1 回の入室で、次の順に問い合わせる。
  1. ルームのページ `/r/<ルーム>` を 1 回開く (uuid が無い時も有る時も 1 回)
  2. `/api/live/live_info` (268 行目)
  3. `/api/live/current_user`
  4. `/api/room/greeting`
  2〜4 は、そのルームのページを Referer に付ける。
- 訪問者の印 (uuid) は、`entrance_uuid.json` に残した値 → 無ければログインの Cookie の uuid → それも無ければ
  ページで受け取った値、の順で決め、`_remember_uuid` で残す。時刻で取り直す処理は無い (下の 2)。

ただし、次の時は 1 つの配信で live_info が 2 回以上になる:

- greeting が断られ、残した uuid を消して取り直す時 (`_enter` 234〜236 行目)。1 回目の live_info は前の uuid で呼ばれている。
- 入室に失敗した配信は、次の確認でまた入る (`ENTER_TRIES` = 3 回まで)。失敗のたびに live_info を呼ぶ。

### アカウントは、サーバーがログインしているブラウザの Cookie か → そう

- `keeper.py` 633・637 行目: `AllRoomsEntrance` と `RoomEntrance` に `ctx.cookies` を渡す。
- `ctx` は `new_context` (keeper.py 198 行目〜) で、保存済みのログイン状態 (`state_file`) を読み込んだブラウザのコンテキスト。
  視聴のページ (`page_factory(ctx, ...)`) とログインの維持 (`ensure_login(ctx, ...)`) と同じもの。
- `_enter` は入室のたびに `await self._cookies()` を呼び、その時点の Cookie を取り直す (231 行目あたり)。
- `Session` は `showroom-live.com` の Cookie だけを持つ (45〜52 行目)。
- 回数が進むのは、このログイン状態のアカウント。ログインしていない時は greeting が 401 になり、入室済みにしない
  (テスト `test_not_logged_in_is_not_counted_as_entered`)。
