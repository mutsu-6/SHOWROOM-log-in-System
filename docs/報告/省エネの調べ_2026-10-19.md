# 時間を短くできる所・負荷を減らせる所の調べ 2026-10-19

Cursor がサーバー (e2-small・2 コア・メモリ 2GB) で、19:20〜20:00 (日本時間) に測りました。何も変えていません (読むだけ)。
道具: プロセスごと・スレッドごとの CPU とディスクの書き込み (/proc)、py-spy (Python の中のどこで時間を使っているか)、strace (どのファイルに書いているか)。

## 全体
- コンテナの CPU は 1.1〜1.5 コア分 (瞬間で 3.2 コア分のことも)。メモリの空きは 0.7GB。ディスクへの書き込みは 1 分に約 100MB。
- CPU の内わけ (1 分間): ブラウザ (配信中の応援ルーム 2 つのページ) が 約 60%、Python 本体が 約 47%。
  - ブラウザ: ページ 2 つで 25%・20% (1 つ 480MB)、音声の処理 7.5%、通信 5%、画面 4%
  - Python: いちばん多いのは収集 (sweep) のスレッド

## 1. 収集 (sweep) が、仕事のたびに空振りの問い合わせを 2 つしている (いちばん効く)
- `room_analysis.step` (sweep の仕事 1 つごとに呼ばれる。1 秒に 2 回ほど) の次の 2 つの SQL が、毎回 100〜150 ミリ秒かかる。どちらも、ほとんどいつも 0 件。
  - room_analysis.py:596 `SELECT event_id FROM events WHERE progress_at IS NOT NULL AND end IS NOT NULL AND end < ? AND style_at IS NULL …` 1 回 104 ミリ秒
  - room_analysis.py:607 `SELECT event_id FROM events WHERE style_at IS NOT NULL AND thinned_at IS NULL AND end < ? …` 1 回 149 ミリ秒
  - どちらも events_end の索引で「終わった全部のイベント」(3 万件) を順に見て、1 件ずつ表を引いている
- sweep のスレッドが使った時間の 約 3 分の 1 がこの 2 つ。CPU にすると 0.2〜0.3 コア分を、ずっと使っている。
- 直し方の案: 部分の索引 (`WHERE style_at IS NULL` / `WHERE thinned_at IS NULL`) にするか、0 件だった時は 1 分ほど調べない。
- 受け持ち: Claude Code (room_analysis.py・sweep.py)

## 2. 配信中のルームの一覧 (/api/live/onlives・1.1MB) を、3 か所で別々に取っている
- 全ルームの入室 (entrance) が 60 秒ごと、ギフトの記録 (recorder) が 120 秒ごと、収集 (sweep) が 300 秒ごと。1 分に約 1.7 回、1 日に約 2.7GB を受け取っている。
- 入室と、視聴の配信状況 (room_status) は、ブラウザ (Playwright) を通して問い合わせている。Playwright は呼ぶたびに呼んだ所を記録する (`inspect.stack`) ので重く、Python の CPU の 約 1 割がこれだった。1 回の一覧の読み込み (json) にも 0.24 秒かかる。
- 直し方の案: 一覧は 1 か所で 60 秒ごとに取って使い回す。ログインの要らない問い合わせ (一覧・配信状況) は、ブラウザを通さず urllib で取る。
- **直した** (Cursor・[PR #38](https://github.com/mutsu-6/SHOWROOM-log-in-System/pull/38)。結果は `Cursorの作業_2026-10-19.md`)

## 3. 配信のページ (ブラウザ) が、CPU とメモリをいちばん使う
- 応援ルームが 2 つ配信中だと、ページ 2 つで CPU 約 45%・メモリ 約 1GB (音声などを入れると CPU 約 60%)。画質は「medium」(既定)、音は消している。
- 画質を「low」(`.env` に `SHOWROOM_VIDEO_QUALITY=low`) にすると、映像を開く仕事が減って軽くなる見込み。視聴の数え方・アバターに影響が無いかを確かめてから決める。

## 4. ディスクへの書き込みが多い (1 分に約 100MB・1 日に約 140GB)
- ほぼ全部が sweep の research.db への書き込み (WAL に書いてから本体に写すので 2 回書く)。貢献ランキング 1 件 (100 人) ごとに、索引 (人で引くもの) のばらばらの場所を書き直すため。
- そのほか、SQLite が並べ替えの途中を `/var/tmp/etilqs_*` に書き出している (40 秒で 8 個・合わせて約 2MB)。
- 今はディスクに余裕がある (15GB / 29GB) ので急がない。

## 5. 管理画面を開いた時だけ重い所 (開いていなければ動かない)
- `event_analysis.api_lag` (イベントの一覧で使う): 1 時間に 1 回、記録した全ルームの live_events (732 ファイル・12MB) を読み、11 秒かかる。
- 「収集」の全体の件数 (`research.store_status`): 10 分に 1 回、6〜9 秒。
- ギフターの一覧を先に数えておく (`listing.warm_listeners`): 10 分ごとに約 12 秒 (0.02 コア分)。一覧を開いていない日も数えている。
