## 二重に数えた所 (私の測りが原因とみられる)
- `update_gift_senders` (と `update_gift_events`) は、どこまで読んだか (`gift_sender_pos`) を、書き込みのトランザクションの外で読む。
  同じプロセスの中では `_sender_lock` で守られるが、**別のプロセスとは守られない**。2 つのプロセスが同じ所から読むと、同じギフトを 2 回足す。
- 私が 14:59〜15:05 に別のプロセスで `_analyze_view` を測った時、その中で記録の新しい分を書き足していた (`update_all_gift_senders`・1,154 ルーム)。
  同じ時に本体の裏の仕事 (catchup) も足していたとみられる。
- 15:15 に全ルーム (1,154) で、読んだ位置までのファイルの行の数とくらべた:
  - `gift_room_totals` と `gift_senders` の回数の合計: 8 ルームで 1〜20 件多い (1,753 → 1,760 など)
  - `gift_events`: 4 ルームで 2〜84 件多い (4,194 → 4,278 など)
- 14:24 に 25 ルームでくらべた時は全部同じだったので、そのあとにできたもの。合わせて、およそ 150 件 (全体 142.8 万件)。
- 直し方の案 (どちらも、利用者か Claude Code が決める):
  - そのルームの分を作り直す (`gift_sender_pos` を消して、ファイルの最初から足し直す。`gift_events` も同じ)。
  - 位置を読む所を、書き込みのトランザクションの中に入れる (Claude Code の受け持ちの `explore.py`)。
- これからの私の測りでは、**書き足す関数を呼ぶものは別のプロセスで動かさない** (`_analyze_view`・ギフターのページなどは、管理画面を通して測る)。
- **直した (17:00〜17:25。利用者が「該当ルームを最初から数え直す」を選んだ)**:
  - 3 つの表それぞれの読んだ位置で数え直すと、ずれていたのは **10 ルーム** (送り主の表 8・ギフト 1 件ずつの表 4、うち 2 つは両方)。
    上で「8 と 4」と書いたのはこの 10 ルーム。日ごとの表 (`room_gift_daily`) は、10 ルームともずれていなかった。
