# Cursor への依頼: 戦力ランキングの物差しの候補を写しで採点する (2026-11-13、Claude Code から)

Cursor の提案「ギフターの強さのランキング: 物差しの見直し」(2026-11-13) を、M さんが「取り入れよ」と言った。
提案の「古いほど軽く数える量」と「決定力」を、`backtest.py` の候補に足した (プルリクエストのブランチ `claude/project-thread-74sr0j`)。
**写しで動かすだけ**。サーバーでは動かさない。ギフターの名前・ID は報告に書かないでください (結果の JSON にも入らない)。
結果は `docs/報告/Cursorの作業_<日付>.md` に。

## 動かし方

プルリクエストのブランチを取ってきて、Mac の写しで:

```
python -m showroom_keeper.backtest <写しのあるフォルダ> --sample 2000 \
  --at 2026-04 --at 2026-05 --at 2026-06 --at 2026-07 --at 2026-08 --at 2026-09 \
  --dev 2026-04 --dev 2026-05 --dev 2026-06 --out backtest-measure.json
```

- 10/27 は 3 か月・2,000 人で 889 秒・メモリ 220MB だった。6 か月なので 30 分ほど (推測)。決定力の分は 1 人 2 回の小さな問い合わせが増えるだけ
- 4〜6 月が開発の期間 (候補を選ぶ)、7〜9 月が確かめる期間 (入れるかを決める)。同じ月で選んで同じ月で褒めないため
- 終わったら、画面の最後に出る「見込み量の式の候補」の 3 つのかたまり (全部の月・dev・check) を、そのまま貼ってください。
  各かたまりの最後の「決め手の数え方」の行も
- かかった時間と、メモリの最大 (`/usr/bin/time -l` の maximum resident set size) も

## 足した候補

| 名前 | 中身 |
|---|---|
| decay_h1・h2・h3 | 現役の強さ (Cursor の案): 直近 12 か月の月ごとの量を、古いほど軽く足す。重みが半分になる月数が 1・2・3 か月 |
| appear_med3 | 直近 6 か月で送った月の割合 × 直近 3 回の中ほど (ギフター × ルームの採点で、出てきた時の量は直近 3 回の中ほどが火力より外れが小さかった) |
| decisive_past | 決定力 (Cursor の案): 過去 12 か月の勝負の回で、その人の量が、すぐ下の順位のルームとの差より多かった回の数 |

列の「次の勝負で決め手になるか」は、次の 30 日の勝負の回で、その人の量がすぐ下のルームとの差を上回ったかを、どの候補がよく当てるか (AUC。でたらめなら 50%)。

## 結果の読み方 (結果を見る前に決めておく)

1. 重みが半分になる月数は、**dev** の「並び」がいちばん高いものを選ぶ (同じなら「出てくるか」)
2. 選んだものを、**check** で「先月の量」とくらべる。並び・出てきた人どうしの並びの両方で上なら、画面の並びに入れる
3. 勝てなかった時も、今の総合力 (10/27 で並び 55%) より「先月の量」(81%) の方が当たっているので、並びは「先月の量」か「最近 90 日の量」に変える案を M さんに出す (何も考えない予測そのものなので、式の変更の決まりには当たらない)
4. 決定力は、check の「次の勝負で決め手になるか」で、先月の量より上なら、並びの横の列にする。下なら、過去の事実の列としてだけ出すかを M さんに聞く
5. 「決め手の数え方」の行で、block の付いたイベントの回の割合が大きければ、ブロック分けのイベントの確認 (`Cursorへの依頼_2026-11-11_ブロックの返し方.md`) が済むまで、その回を外して数え直す

## このプルリクエストで変えたもの

- `showroom_keeper/backtest.py`: 候補 4 つ・決定力・`--dev` で期間を分けて採点。採点の線 (当たりの決め方) は変えていない
- `admin.html`: 戦力ランキングで、信頼度「参考」(1 回だけ・1 か月だけ) の人を、初めから除く (押すと出す。消してはいない)。除いた人数をボタンに出す
- 並べ方の式 (総合力) は、まだ変えていない

## 2 回目 (2026-11-13 22 時、M さんの「その月・週・日ならどうか」「当月をデータ補正しながら予想した方が」から)

1 回目の結果 (`Cursorの作業_2026-11-13_戦力ランキングの物差し.md`) のあと、答えの線と候補を足した。

- 答えの線 (画面の最後の 3 列):
  - **その月の残りの合計の並び**: 時点のあとに、その月のうちに終わったイベントで出した量の合計 (全部のルームを足す。出さなかった人は 0)
  - **その月の残りの、出した人どうしの並び**
  - **その月全体の合計の並び**: 月の途中の時点なら、もう分かった分も入る (分かった分の多い人が上に来るので、当たりは自然に上がる。腕前は「残り」の方で見る)
- 候補 (月の途中の時点で、その月に終わったイベントで分かった分を使う):
  - `so_far_extrap`: 今月ここまでの量を、月の残りの日数の分だけ伸ばす (何も考えない予測)
  - `so_far_month`: 今月ここまでの量 + 先月の量 × 月の残りの割合
  - `so_far_decay`: 今月ここまでの量 + 古いほど軽く数えた月の平均 × 月の残りの割合
- `--day 15` で、時点を各月の 15 日 0 時にする (既定は 1 日)

同じ写し (11/12 04:00) で、次の 2 つを動かしてください (合わせて 1 時間ほどの見込み)。それぞれ 3 つのかたまりを、そのまま貼ってください。

```
python -m showroom_keeper.backtest <写しのフォルダ> --sample 2000 \
  --at 2026-04 --at 2026-05 --at 2026-06 --at 2026-07 --at 2026-08 --at 2026-09 \
  --dev 2026-04 --dev 2026-05 --dev 2026-06 --day 1 --out backtest-measure-day1.json

python -m showroom_keeper.backtest <写しのフォルダ> --sample 2000 \
  --at 2026-04 --at 2026-05 --at 2026-06 --at 2026-07 --at 2026-08 --at 2026-09 \
  --dev 2026-04 --dev 2026-05 --dev 2026-06 --day 15 --out backtest-measure-day15.json
```

結果の読み方 (見る前に決めておく):
- 月の初め (`--day 1`) の check で、「その月の残りの合計の並び」がいちばん高い並べ方を見る (先月の量・最近 90 日・古いほど軽く数える量)
- 月の途中 (`--day 15`) の check で、「その月の残りの合計の並び」が、何も考えない予測 (`so_far_extrap` と先月の量) より `so_far_month`・`so_far_decay` の方が高ければ、月の途中で見込みを直す意味がある。
  「その月全体の合計の並び」は、分かった分が入るので高く出て当たり前。これだけで褒めない
- この採点は「イベントが終わった時に、すぐ貢献ランキングが分かった」とする遡及の比較。サーバーでは終わってから読むまで時間がかかるので、本当はこれより少し悪い
- 週・日は、ギフターごとの量が貢献ランキングに無い (イベントの終わりの累計だけ) ので、ここでは採点しない
