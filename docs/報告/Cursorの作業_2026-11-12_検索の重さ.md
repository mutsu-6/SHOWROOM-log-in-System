# Cursor の作業の報告 2026-11-12 検索の重さ

上の検索欄に短い言葉を入れると、画面が「探しています…」のまま止まりやすかった。ギフターの名前は出さない。

## 検索の要求がしていたこと

名前の索引 (`search_users`) が出来ているときでも、検索の要求は次の 2 つをしていた。

- 当たった人 (最大 1000 人) ごとに、`user_room` から `SUM(MAX(cumulative, events))` を足して並べる
- 記録したギフトの送り主 (`gift_sender_names`) を、`instr(folded, ?)` で表の最初から最後まで見る

この機械には本番の `research.db` が無いので、本番のディスク (空きが少なく、貢献の記録が 1 日に数百 MB 増えている) での秒数は測っていない。読み方 (EXPLAIN QUERY PLAN) は、前の送り主の検索が `SCAN gift_sender_names`、今の 3 文字以上が `search_senders` の索引、ポイントが `users.shown_points` の列である。

## 直し方

- `users.shown_points` を、累計ランキングと貢献ランキングを保存するときに作り直す。検索はこの列を読む
- まだ空の人は、収集の合間と、ページを開いたあとの裏の足し分で、少しずつ埋める。埋まるまでは、その人のポイントは検索結果に出ない (名前は出る)
- 3 文字以上の送り主は、`search_senders` (trigram。名前の索引の VERSION とは別で、入れ直さない) で引く。新しく記録した名前は、送り主の表に足すとき一緒に入れる。前からある名前は、収集の合間に少しずつ入れる。入れ終わるまでは、その送り主は 3 文字以上の検索に出ない
- 2 文字以下は索引で引けないので、今まで通り名前の表をくらべる

## この機械で測ったこと

本番のデータベースではない。名前が「wata」に当たる人 1000 人 (1 人あたり `user_room` 15 行) と、送り主の名前 8 万行で、温めたあとの中央値は前の SQL が 0.006 秒、今の `explore.search` が 0.003 秒。SSD で表がメモリに入っているので、本番の待ち時間にはならない。

送り主の名前を 108 万行まで増やすと、`instr` の全走査は 0.063 秒、索引は 0.001 秒未満 (どちらもこの SSD、温めたあと)。行が増えると全走査だけが遅くなる。

管理画面で「wata」を入れると、ドロップダウンにギフター 40 件とルーム 20 件が出て、「探しています…」は残らなかった。開いた人のページには保存してあるポイント (10万 pt) が出た。`pytest` は 526 件成功。
