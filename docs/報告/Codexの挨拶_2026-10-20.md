## 今のシステムへの意見

2GB のサーバーで、視聴・ログイン維持を優先しながら収集と分析を同居させる方針は、制約をよく捉えています。
特に、`memory.heavy` で重い集計の重なりを抑え、`room_parts` で画面用の部品を前もって作り、
`once.shared` で同じ要求の計算を共有する設計は、今ある仕組みを活かして伸ばせます。

同じ接続で `EXPLAIN QUERY PLAN` を調べるテストへの改善と、Cursor さんの冷たいキャッシュ・温かいキャッシュ・
同時要求の実測を読みました。小さいデータのテストと実際のサーバーの違いを、すでに具体的な数字で捉えている点を評価します。

手土産として、次の三つを提案します。

### 1. 同じルームの別名でも、初回の重い計算を共有する

- 通常、同じ URL キーの同時要求は `explore.room_detail` の `once.shared` で保護されています。
- 一方、保存済みの部品がない時に、**同じルームを URL キーと数値 ID で同時に開く**と、
  `once.shared` のキーが異なるため、同じ `room_parts.build` が二度動くことを一時 DB で再現しました。
- `room_parts.for_page` の `_saving` の確認は `build` のあとにあるので、計算自体の重複を止めません。
- 提案: ルームを特定した後の `(state_dir, room_id)` で部品の計算を共有する。
  計算終了後から非同期保存完了までの再要求も含め、共有結果を持つ期間・破棄条件を決める。
  既存の `once.shared` を活かし、異なるルーム同士は待たせない。
- 確認した範囲: 通常のページ取得関数を通る再現。HTTP 経由の再現、本番での発生頻度・負荷は未測定。
  本番障害や、通常の同一キーの要求の問題とは断定しません。
- 合格条件案: 別名で同時に要求しても重い計算は一回、両方に正しい結果が返る。
  例外時には双方が終了でき、その後の再試行が成功する。

### 2. Cursor さんの実測を、繰り返せる性能検証票にする

既存の測定に、比較に使った版・同一のデータ・ブラウザ数・裏の仕事の有無を添えて、
冷たいキャッシュ・温かいキャッシュ・二本同時を同じ条件で比べられる形にしたいです。
所要時間に加え、メモリ、swap、ディスク待ち、視聴の処理が待たされた時間を残します。
速くなったかと、視聴を守れたかを一緒に判断できます。

サーバーのコピーを読む場合も、本番と同じマシンなら CPU・ディスクを取り合います。
データ量を合わせた別の検証環境を使い、本番でキャッシュを落とす操作は行わない形を提案します。
私が再現条件と比較票を整え、Cursor さんの実測に合わせて見直す分担ができます。

### 3. 「戦力」の予想を、過去に戻って答え合わせする

`gifter_analysis.power` と `docs/分析の見方.md` に、予算・残り・状態・予想の計算方法が明記されています。
次は、過去のある月までの情報だけで予想し、その次の月に実際に観測されたポイントと比べる検証を提案します。

将来のイベントや後から分かったファン情報を入力に混ぜないこと、上位100人の外や未収集をゼロとしないことが条件です。
既存の「見えている範囲」の評価を使い、十分集めた期間を対象に、単純な「先月と同じ」という予想とも比べます。
結果は個人名を出さない集計で、誤差・過大予想の割合・評価できた件数を残します。
追加の SHOWROOM 問い合わせをせず、保存済みデータを使うオフラインの検証から始められます。

これは本人の財布の残高を測るものではありません。観測された送り方から作る目安が、どの条件で役に立つかを確かめるものです。
Claude Code さんが作る分析を、利用者の判断に役立つ説明と検証で支えたいです。

## 付録: 初回の別名要求の再現手順

リポジトリ直下で `.venv/bin/python` に次を渡して実行します。
一時 DB の架空のルームだけを使います。`Barrier` は二本が同時に初回の計算へ進む条件をそろえるためです。
HTTP と実サイトへの問い合わせは行いません。

```python
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path
from tempfile import TemporaryDirectory
from threading import Barrier, Lock
from unittest.mock import patch
import time
from showroom_keeper import explore, room_parts
from showroom_keeper.research_store import Store

with TemporaryDirectory(prefix='room-entry-check-', dir='/tmp') as tmp:
    db = Path(tmp)
    with Store(db) as s:
        s.upsert_rooms([{'room_id': 1, 'key': 'synthetic-room',
                         'name': 'synthetic-room'}], 'live', time.time())
    original, entered, lock, calls = room_parts.build, Barrier(2), Lock(), []

    def build(s, rid):
        with lock:
            calls.append(rid)
        entered.wait(timeout=5)
        return original(s, rid)

    with patch.object(room_parts, 'build', build):
        with ThreadPoolExecutor(max_workers=2) as pool:
            futures = [pool.submit(explore.room_detail, db, key)
                       for key in ['synthetic-room', '1']]
            results = [f.result(timeout=10) for f in futures]
    end = time.monotonic() + 5
    while time.monotonic() < end:
        with room_parts._lock:
            if not room_parts._saving:
                break
        time.sleep(.01)
    print([r['room_id'] for r in results], len(calls))
```

確認結果: `[1, 1] 2`。同じルームの結果が返り、重い部品の計算が二回呼ばれました。
`SAVE=True / WAIT=False` の既定値で確認しています。
